# Word 纯转图接口与工具

本次新增独立转换链路，不调整产品版本，不打包或发布。先部署包含新接口的 Server，再安装包含新工具的插件。旧插件仍使用原接口；Server 1.2.3 未包含该能力时，新工具提示升级，不回退。

## 使用与边界

原生 Agent 工具 `word_to_images` 接受工作区内的 `sourcePath`，以及可选的 `startPage`、`maxPages`、`timeoutMs`。默认为第 1 页、10 页一批、120 秒；单批最大 100 页。先查看正文及结构，有需要时转图，再通过 `read` 按真实页码读取 PNG。图片已经转换不等于模型已经理解。

扩展从当前 ChipMate Server 地址派生 `/convert/word-to-images`，通过 `CHIPMATE_WORD_TO_IMAGES_ENDPOINT` 传给 CLI。沿用进程环境显式覆盖语义，不允许模型在工具参数中传上传地址。原文件不变；图片、来源 SHA-256、页码及中文转换记录保存在当前产品的 artifacts 目录。

`POST /convert/word-to-images` 请求 JSON 包含 `filename`、`docxBase64` 及上述分页、超时字段。只支持 DOCX。成功返回 `ok`、`pageCount`、`returnedPageCount`、`startPage`、`nextPage`、`pages`、`issues`、`renderer`。每项页面包含 `page`、`contentType`、`width`、`height`、`base64`。末批 `nextPage` 为 null。工具不把 Base64 放入文本结果。

输入错误返回 400，体积超限 413，页码越界 422，转换失败 500，超时 504。空白页保留并给出诊断。每次转换使用独立临时目录与 LibreOffice 配置；取消只终止本次进程组，并等待退出后清理。

转换使用 LibreOffice 导出临时 PDF，再由 Poppler 生成指定页 PNG；不会执行旧服务的目录刷新、页码回填或交付检查，不返回 PDF 或更新后的 Word。页面布局及域的显示仍由 LibreOffice 导出引擎决定，不承诺与 Microsoft Word 完全一致。

## 验证依据

目标用户为读取详设图页的开发人员。人工基线为手工导出文档、定位页码、保存图片再交给模型。支持范围是正常可由现有 LibreOffice 打开的 DOCX，输出与页码必须一致，错误和取消不得伪报成功。当前没有真实人工耗时对照，不宣称减少人工 80%。

- 真实 Fastify 路由及 LibreOffice／Poppler：固定样本能触发旧逻辑“TOC entry count 0 does not match PDF outline count 20”，新路径成功；覆盖分页、末页、越界、非法输入、损坏归档、无目录空白页保留、1 毫秒超时、取消清理及并发请求。
- 固定样本包含目录域、20 个标题、公式、合并表格、嵌入流程示意图、交叉引用和修订。两份仓库 UFS 样本分别返回 3 页和 1 页，已查看实际 PNG。样本不是内网现场原文。
- 原生 `/spec` 命令进入标准 Agent，新工具真实调用 Server；后端真实消息进入当前 ChatView，点击真实页码链接产生文件打开消息；随后原生 `read` 将 PNG Base64 作为图片传入脚本模型请求。移除真实工具消息后不能展示图片入口。
- 协议反例覆盖旧接口、缺失图片、错误页码、无效 PNG 及已取消请求，均拒绝接受，不调用旧接口、不创建产物。
- 隔离的真实 macOS VS Code 1.93.0 扩展宿主实际执行生产文件打开处理器，确认生成图片进入 `imagePreview.previewEditor`，测试进程退出码为 0；没有改动用户 Profile。
- 扩展处理器单测确认图片调用原生 `vscode.open`，不作为文本打开；发送契约与图片打开测试合计 65 项通过。端点与既有产物卡片相关测试通过。
- 旧 Word 生成/渲染、目录刷新、PDF 目录回填、Mermaid、PlantUML 相关 13 项测试通过。

浏览器测试使用脚本模型和真实前端，证明消息与图像接口接入，不能证明真实模型理解公式、准确识图或遵循 Skill。远程 Linux、内网 Server、Windows 与 Qwen 效果仍需目标环境验证；模糊图片的模型判断未实测。
