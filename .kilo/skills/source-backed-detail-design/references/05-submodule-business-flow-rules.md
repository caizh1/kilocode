# 05 Submodule Business Flow Rules

本 reference 约束的是代码级子模块详细业务/逻辑流程图，重点展开函数调用、源码条件、状态读写、数据流和异常路径。high-level 业务流程图由 `15-business-flow-abstraction-rules.md` 约束，二者不得互相替代。

## 1. 子模块图必须回答的问题

子模块从哪里被触发；进入条件是什么；处理哪些数据结构；调用哪些关键函数；判断哪些状态/标志/返回值；什么条件进入等待/重试/错误/完成；对父模块状态或数据有什么影响；与其他子模块如何交互。

## 2. submodule-flow-evidence.md

每个子模块必须包含 Submodule overview、Responsibility、Scope boundary、Entry triggers、Input/Output objects、Participating functions、Business flow steps、Data flow、Terminal paths。

## 3. 子模块图最低要求

每个重要子模块图必须覆盖真实入口、完整业务动作、源码中存在的条件分支、数据结构读写、下游调用、正常完成、错误/等待/重试/恢复路径、可读边 label 和 edge coverage。源码确实不存在某类分支时记录证据，不通过虚构节点满足数量要求。图本身质量不得因增加文字说明而降低；文字说明应写在正文和证据文件中，不把大段说明塞进 Mermaid 节点。

每个重要子模块还必须拥有独立的架构图、high-level 业务流程图、代码流程图、状态机图和数据/生命周期图。状态机只有在源码确实不存在状态、phase、event、dispatch、handler、lifecycle 或 transition 语义时才可标记为 `N/A`，并写出证据；不得静默省略或虚构状态。五类图可以共享证据，但不能用同一张图重复充当不同视图。

## 4. 无效图

只有函数 A -> 函数 B -> 函数 C 的图无效。缺少业务条件、状态、数据流、异常路径的图不能进入正文。

## 5. 图与正文绑定

每个子模块图必须在该子模块自己的连续详细设计章节中就地引用，并配套子模块简介、职责边界、步骤表、数据流表、异常路径表和源码证据表。逻辑文件仍可使用原有业务流或代码流路径，但 Word 组装时不得把同一子模块的两类流程拆散到互不相邻的全局章节。

## 6. 与 high-level 业务流程图的边界

代码级子模块图可以出现函数名、结构体字段、状态变量和返回值；high-level 业务流程图的主节点不得以这些源码符号命名。

代码级子模块图用于解释“源码如何实现业务流程”；high-level 子模块业务图用于解释“业务上发生了什么”。如果两类图只生成了一类，最终质量门禁不得 PASS。


## 7. 子模块文字简介要求

每个重要子模块在正文中必须有图前文字简介，禁止只放一张架构图或流程图。简介不设固定字数，但必须覆盖：

- 子模块在父模块中的业务定位；
- 主要触发来源和进入条件；
- 处理的核心业务对象、数据结构或状态；
- 正常情况下交付的结果或副作用；
- 典型异常、等待、重试或终止路径；
- 与上下游子模块的衔接关系。

文字简介必须基于源码证据或业务抽象证据。没有源码证据的内容只能写入待确认事项，不能写成确定结论。

## 8. 图文配比

子模块业务流部分的推荐顺序为：

1. 子模块简介；
2. 职责与边界；
3. 输入/输出业务对象；
4. high-level 业务流程图；
5. 图后流程解读；
6. 关键步骤表；
7. 异常/等待/重试路径；
8. 源码证据表。

在同一子模块章节中，业务流部分之后还必须按 `10-detail-design-output-templates.md` 就地呈现数据/生命周期、代码流程、状态机或证据化 `N/A`、接口、异常恢复、策略性能、构建集成、可观测性和证据缺口。high-level 业务图和代码流程图必须分别生成，不再使用“二选一”表达。

不得为了增加说明文字而降低 Mermaid 节点、边 label、状态/数据/异常路径的既有质量。
