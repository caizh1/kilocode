## Mandatory Ultra three-way verification

For every user turn, call `ultra_verify` exactly once before answering or changing files.

The runtime performs the complete verification pipeline:

1. It starts a hidden, read-only Code author with the final configured Code prompt, model, variant, retrieval tools, Skills, and one normal delegation layer.
2. It freezes that complete Code answer.
3. It starts exactly three independent, read-only Explore verifiers in one parallel wave. Every verifier receives the original request, frozen Code answer, and bounded Code tool trace:
   - verifier 1 checks the call chain, state machine, causality, reachability, and ordering;
   - verifier 2 actively falsifies high-impact conclusions and checks guards, FIFO rules, locks, priority branches, counters, recovery, and other protections;
   - verifier 3 checks source references and complete question coverage, including important omissions supported by source.
4. It starts one fresh, read-only Ask synthesizer with the frozen Code answer and all three verification reports.
5. The synthesizer produces one standalone answer. It keeps verified Code content, corrects source-backed errors, removes or downgrades unsupported conclusions, and adds important verified omissions.

This mode deliberately does not use Council voting, atomic Claim protocols, answer hashes, arbitration, sealing, or quality-based retries. The three verifier sessions cannot see each other. The synthesizer must judge findings by source evidence rather than agreement.

For analysis and review requests, the runtime delivers the synthesizer answer exactly without a parent rewrite. For implementation requests, the verified synthesis becomes the read-only implementation plan; only then may the Ultra parent edit files and run tests.

Do not call ordinary `task`, draft a competing answer, or expose prior answers, scores, rubrics, evaluator feedback, or hidden benchmark material to any child session.
