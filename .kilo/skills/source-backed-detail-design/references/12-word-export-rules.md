# 12 Word Export Rules

## 1. Kilo Word route

When the user asks for Word output, generate the `.docx` with Kilo's generic Word tools. Use `create_word_document` for the initial working document and `apply_word_document_edits` for bounded non-image chapter batches. The tool-created working artifact is continuation evidence, not the final user deliverable. Do not introduce a task-specific Word pipeline, temporary JSON shell bridge, local Pandoc, local LibreOffice/soffice authoring, `pip install`, `npm install`, `python-docx`, or a standalone Python/Node DOCX script as the primary or fallback route. `08-word-export-input.md`, when used, is an auditable assembly draft, not the final export mechanism or tool payload.

## 2. create_word_document arguments

Before calling `create_word_document`, verify the required Word tools are exposed and prove prose readiness from `02-source-evidence/module-scope.md`, the frozen DesignUnit census, every `05-enhanced-detail-design/units/<designUnitId>.md`, and root-level `resume-state.md` plus `review-notes.md`. The resolved target must be distinct from every evidenced owning module; decomposition, census, unit, detailed-chapter and diagram-ledger sets must be identical; every fourteen-topic entry must be explanatory `PASS` or evidenced `N/A`. Then require diagram readiness with `expectedBaseSlots = 5D - evidencedStateMachineNaCount`, `missingSlotCount = 0`, and `duplicateDiagramIdCount = 0`, and freeze the final ordered outline. Any missing or duplicate unit, topic, explanation, exception path, evidence, diagram, or safe workspace file-writing capability keeps Word state `not_started`; preserve the continuation state and do not call the Word tool.

Build object-shaped top-level arguments with the authoritative dynamic `title`, `language: "zh-CN"`, an informative dynamic `documentType`, `author`, `headingNumbering: "decimal"`, summary paragraphs, and `sections`; never wrap or stringify them. `documentType` must describe the source-backed scope actually covered, add information beyond the title, and never be only “详细设计”, a title repetition, a generic placeholder, or an unsupported claim. Pass `author: "ChipMate source-backed-detail-design"` by default so both the visible author line and DOCX creator metadata use that identity; an author explicitly supplied by the user takes precedence. Never invent an author containing Kilo, Kilo Code, or a similar variant. Choose a stable `taskSlug`; use a clearly non-deliverable `*-working.docx` output name during assembly and reserve the intended final filename for the completed field-refresh chain.

Keep a formal page-1 cover. Before the sole `{{TOC}}` item, include concise Normal-paragraph cover statements for document scope, current source baseline, and evidence status. Derive them from the frozen scope and evidence files; omit an unavailable fact or mark it `待确认` instead of inventing it. Keep these statements compact and do not place chapter prose, large tables, code, or images on the cover. The materialized TOC intentionally starts on page 2.

A full detailed design uses a text-only initial working skeleton containing the real tool-level title, informative subtitle, approved author, compact cover statements, exactly one standalone summary paragraph whose full text is `{{TOC}}`, every final H1/H2/H3 heading in frozen order beginning with Heading 1 `阅读路径`, and one unique Normal-paragraph anchor `[[SBDD-CONTENT:<designUnitId>:<topicId>]]` for every bounded prose/table batch. The cover summary list must end with `{{TOC}}`. The skeleton contains no image blocks, handwritten directory, long prose, large tables, long lists, or code bodies. Do not create it from only the first few completed submodules. Do not embed an anchor or `{{TOC}}` in other text, repeat an anchor, or omit headings to reduce the payload.

After skeleton creation, fill non-image content in canonical order with strictly serial `apply_word_document_edits` calls. Use `replace_paragraph_with_blocks` with the exact anchor in `locator.paragraphText`; one main chapter or confirmed-submodule design unit is the maximum batch size. Split a larger unit across its predeclared topic anchors, consume every anchor exactly once, and pass every newly returned Word path into the next mutation. Never use `insert_after_heading`, `append_blocks`, a sibling working path, or a document-end fallback when an anchor is absent or ambiguous; repair the exact skeleton anchor first. Structural edits cannot add image blocks.

When the last prose/table mutation succeeds, inspect before any image insertion. Require the complete frozen outline, zero `[[SBDD-CONTENT:*]]` paragraphs, `paragraphsTruncated: false`, `tablesTruncated: false`, completed DesignUnit count equal to the frozen census, and explanatory body in every final heading's own local range. Body means explanatory Normal/code paragraphs before the next heading of any level; aggregate fourteen-topic coverage is checked separately per DesignUnit. Empty paragraphs, directory material, image title/caption/figure ID, drawings, anchors, and standalone lists or tables do not count. Container headings require their own short orientation paragraph before the first child heading. Repair every empty, image-only, list-only, table-only, inventory-only, or one-line-name section before continuing.

Only after this body audit passes, insert every PNG serially through `insert_mermaid_into_word`. Even when `pngPath` exists, pass the exact Mermaid text in `source`, the latest `wordPath`, unique existing H2/H3 `heading`, stable `taskSlug`/working `outputFile`, source-mapped `pngPath`, plain Chinese `figureTitle`, complete independent Chinese `altText`, and unique visible caption. If multiple diagrams belong immediately after one heading, invoke them in reverse intended display order because each insertion is placed directly after that heading.

If a large call fails, reduce it to the text-only working skeleton rather than writing the payload to a temporary file or retrying the same oversized object. Split a failing chapter until the smallest meaningful topic anchor is isolated. If that mutation still fails, preserve the persisted Markdown unit files and exact continuation point, disclose the native tool error, and do not present the working DOCX as a deliverable. Do not replace the failed detailed subsection with a one-line summary or switch to a third-party generator.

Sections must preserve the hybrid structure from `10-detail-design-output-templates.md`: the opening positioning section separates system architecture, source ownership,所属上级模块, calls and target handoffs; chapters 4 through 8 together form the target module DesignUnit, with target architecture in chapter 4, its unique business primary in chapter 6, target-internal decomposition with no diagram slot in chapter 7, and target data/code/state views in chapter 8. Chapter 8 references the chapter-6 business figure without reinserting or recounting it. Chapter 9 then contains one continuous chapter per target-owned confirmed submodule in the exact frozen decomposition-table order, followed by cross-module summaries, indexes, coverage, optional differences, and review items. 所属上级模块 must not acquire target-style chapters or mandatory five-view images. Target implementation chapter 8 must never appear between child chapters, and a later child batch must never be appended after the closing global chapters. Do not assemble all submodule business flows, code flows, state machines, or objects into detached horizontal chapters. The relationship-separation rule applies throughout the document, not only to the opening positioning section.

New detailed-design documents use the Codex `standard_business_brief` baseline: US Letter portrait, one-inch margins, Calibri 11 pt body, the standard blue H1/H2/H3 hierarchy, real numbering, fixed-DXA tables, quiet running header, and right-aligned page number. Put the standalone `{{TOC}}` paragraph after the title/summary and before the first Heading 1 for a full detailed design. After all chapter and late-image mutations, call `materialize_word_fields` with `tocMode: "materialize"`, the stable `taskSlug`, and the stable `outputFile`. The result must be a native Word TOC field with a non-outline directory heading and page separation, not a static list of copied heading text.

Before materialization, inspection must prove exactly one correct Title, one non-empty and non-redundant Subtitle, the approved visible author, at least one evidenced cover statement, exactly one placeholder, and `placeholderParagraphIndex < firstHeading1ParagraphIndex`. The Subtitle must not equal “详细设计” or the Title. After materialization and field refresh, inspection must prove `Title index < TOCHeading index < first Heading 1 index`, zero `{{TOC}}`, and the TOC beginning on page 2. Any violation is structural `PARTIAL` and must be repaired before final delivery.

## 3. Existing-document update and difference output

For an existing-document update, rebuild conclusions from current source and use `apply_word_document_edits`, `apply_word_template_styles`, `materialize_word_fields`, `normalize_word_table_spec`, `merge_word_documents`, or `diff_word_documents` as appropriate. Preserve unrelated user content and styles where the request is a bounded edit. Do not regenerate unrelated chapters or use the old document as current implementation evidence.

A difference-only request may return the requested diff report without producing a new full Word document. A single-chapter, single-submodule, state-machine-only, or quick update uses the same generic Word tools and only the relevant sections; it must not be expanded into the canonical full-document outline unless the user asks.

## 4. Figures and diagrams

Track separate `CoverageSlot` and `DiagramRequirement` ledgers. `CoverageSlot` contains exactly `5D` base rows. `DiagramRequirement` contains one row per actual base or focused figure using `diagramId -> baseOrFocused -> owningSlot -> complexityInstanceIds -> sourceEvidence -> mmdPath -> sourceStatus -> syntaxValidation -> semanticCoverage -> pngPath -> visibleFigureId -> targetSection -> renderDisposition -> visualQaStatus -> wordInsertionStatus`. Do not put drawings into the initial working skeleton. After the complete text-only body audit passes, insert every successfully rendered required Mermaid diagram with this semantic payload:

```json
{
  "wordPath": "<latest working DOCX path>",
  "source": "<validated Mermaid source>",
  "pngPath": "<pngPath returned by render_mermaid_diagram>",
  "heading": "<unique existing H2/H3 heading>",
  "figureTitle": "中文图题",
  "caption": "[DU-<designUnitId>/<viewType>/<diagramId>] 中文图注",
  "altText": "完整的中文可访问性说明，源码符号保持原样",
  "width": 480,
  "height": 280
}
```

The stable visible figure ID appears exactly once, at the start of the caption; the title is plain Chinese and the alt text is a complete accessible description. Use the render result's cropped display width and height and retain pixel dimensions as QA evidence. Word insertion is inline, centered, aspect-locked, downscale-only, and bounded to 624 CSS px wide and 720 CSS px high. If fitting the page makes labels unreadable, split and rerender the diagram instead of shrinking it again. Keep `.mmd` paths in diagram indexes and evidence ledgers for traceability. Multiple figures under one heading are inserted in reverse desired order. If the user explicitly asks for Mermaid source in Word, use a normal code block with Mermaid source; otherwise rendered diagrams must be PNG images.

## 5. Render verification

For a new full document, the text-only working skeleton has no image relationships. Inspect immediately after creation and confirm that the complete frozen target/submodule heading sequence and every expected content anchor exist exactly once before filling prose. After prose filling, record zero remaining anchors and the heading-body audit before the first insertion. Derive `lateInsertedRelationshipIds` after each serial image insertion by set difference; after replacement record `replacedRelationshipIds` and verify that the relationship set did not grow; after an intended removal record only relationships actually absent as `removedRelationshipIds`. Replacing image content normally keeps the relationship ID, and deleting a paragraph or section does not prove its relationship was deleted.

After all prose, image, style, and field mutations, make the final `inspect_word_document` call with `maxParagraphs: 1000` and `maxTables: 200`. Require exactly one Title-style paragraph whose text equals the planned title, no `{{TOC}}`, no `[[SBDD-CONTENT:*]]`, `阅读路径` as the first outline item followed by `术语、范围与证据基线`, exact frozen heading order, zero empty/bodyless heading ranges, completed DesignUnit count equal to the census, and no paragraph/table truncation. Compare final relationship IDs with the expected set using set difference, not planned-count arithmetic. `imageCount` is only a coarse relationship count; it cannot prove content completeness, drawing placement, or semantic identity.

All mutations of one DOCX must be serialized. Parallel Mermaid rendering is allowed, but parallel calls that edit or insert into the same `sourcePath` are forbidden: each output is a sibling fork and later copies can discard earlier figures. Maintain one authoritative working path and pass the path returned by each successful `apply_word_document_edits`, `insert_mermaid_into_word`, style, or field operation into the next mutation. A disclosed coverage-slot, visible-ID, or unexplained relationship-delta mismatch is not completion; sequentially repair the specific defect and reinspect.

The post-repair inspection must compare the final outline, exact heading order, all fourteen local topics for every design unit, later cross-module chapters, per-heading explanatory body, unique caption-only figure-ID paragraphs, table count, and image relationship set with the planned document. It must reject a census that lists more confirmed submodules than complete local chapters, a heading range with no explanatory Normal/code paragraph, a chapter that contains only a name inventory/list/table/drawing/caption, and any target or child unit moved outside the frozen order. Call inspection with `maxParagraphs: 1000` and `maxTables: 200`; require `paragraphsTruncated: false` before using paragraph results as a complete body/visible-ID audit and `tablesTruncated: false` before using table results as complete. Reconcile each actual drawing occurrence to the ledger using `headingPath`, `caption`, visible `[DU-<designUnitId>/<viewType>/<diagramId>]`, `altText`, relationship ID, media path, and content hash. Require zero missing relationships, orphan relationships, missing media targets, duplicate visible IDs, and unexplained duplicate hashes. If either paragraph or table inspection remains truncated, the body audit is not complete and the document cannot pass; page images can diagnose layout but cannot prove missing source-backed prose. `imageCount` alone is insufficient.

For the full detailed-design Word workflow, call `render_word_document` after the relationship and outline checks. The tool tries the configured Render Service first and the local LibreOffice/Poppler path second. Record `pageEvidenceStatus` separately from the skill-owned `pageReviewStatus`; the legacy `visualQaStatus: completed` only means page-image evidence exists. A native TOC is complete only when the render result explicitly reports `fieldRefreshStatus: completed`, returns a valid `refreshedDocxPath`, and reports equal nonzero `tocHeadingCount`, `tocEntryCount`, and `tocPageNumberCount`; an updated DOCX without this status, or a local plain conversion, is not proof of field refresh. Make only that verified refreshed DOCX authoritative, then repeat title, outline, TOC, drawing, relationship, and truncation inspection. After the last mutation or refresh, call `validate_word_document` on the authoritative path. Only `valid` or `repaired` is deliverable; if safe repair returns a new path, that repaired artifact becomes authoritative and must be reinspected and rerendered. An `invalid` result is not deliverable and must not be reported as the final Word path. Open every page PNG at 100%, inspect complex figure/table/code pages again at 200%, fix material risks, rerender the whole document, and repeat the all-page review. Automated page QA, ink ratios, edge checks, or inability to view images cannot be reported as visual pass; if pages cannot actually be opened, set `pageReviewStatus: skipped`. If both render paths are unavailable, continue the Word delivery with `pageEvidenceStatus: unavailable`, disclose the reason, and do not claim page-image visual QA passed. Report DOCX existence separately as `artifactStatus: generated | failed`; report the scoped result as `acceptanceStatus: PASS | PARTIAL`. A generated DOCX with failed TOC refresh or skipped required page review has `artifactStatus: generated` and `acceptanceStatus: PARTIAL`.

## 6. Success criteria

A completed Word handoff reports the final non-empty `.docx` path returned by the complete serial create/edit/repair/render-refresh/validation chain, final `validate_word_document` status, `artifactStatus`, `acceptanceStatus`, confirmed and completed DesignUnit counts, fourteen-topic local coverage, empty-heading count, remaining-content-anchor count, discovery/candidate closure counts, base-view and focused-figure counts, required rendered count, late/replaced/removed/final relationship sets, visually reviewed count, missing count, bounded repairs, paragraph/table truncation status, and final render QA status.

If prose readiness is false, any content anchor remains, any heading range is bodyless, or any confirmed submodule lacks a complete local chapter, do not produce a final-name DOCX and do not report a Word path. The Word tool may already have created an internal working artifact manifest; treat it only as continuation evidence, not as `artifactStatus: generated` or a deliverable. Persist the Markdown units and first incomplete item instead. After prose is complete, a concrete image/render blocker may leave a text-complete generated DOCX with `acceptanceStatus: PARTIAL`, but the final report must distinguish that from missing prose. While native tools remain available and bounded attempts have not failed, continue from the first unresolved item. A Markdown draft, Mermaid source, ASCII diagram, temporary JSON file, `08-word-export-input.md`, or `*-working.docx` alone is not a Word deliverable unless the user explicitly requested only that draft.
