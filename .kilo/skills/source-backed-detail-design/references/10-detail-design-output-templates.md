# 10 Detail Design Output Templates

本 reference 定义完整详细设计的通用章节骨架。它只在 `source-backed-detail-design` 已按原机制加载、且用户明确要求相应交付时使用；不是运行时文档合同，不改变普通 QA。

## 1. 混合式正文结构

完整 Word 默认按以下顺序组织，标题可依据真实模块层级自然化，但不得把代码细节提前到业务定位之前。完整任务先按范围、正文、图形、Word 四阶段执行；正文阶段未证明 readiness 时不得加载 Word payload 或创建 DOCX：

在章节开始前，必须先建立正式封面：真实 `Title`、根据本次范围与证据动态生成且不重复标题的有效副标题、默认作者 `ChipMate source-backed-detail-design`（用户明确指定作者时优先），以及简洁的文档范围、源码基线和证据状态说明。副标题不得只写“详细设计”或其他占位文字；未知封面事实省略或标记“待确认”，不得虚构。封面说明之后放置一个文本严格等于 `{{TOC}}` 的独立摘要段落，再开始第一个真实 Heading 1“阅读路径”。封面保持第一页，原生目录从第二页开始；目录不得手写成 Normal 段落标题列表。

1. 阅读路径；
2. 术语、范围与证据基线；
3. 系统架构定位、所属上级模块与目标模块角色；
4. 目标模块职责、边界与架构；
5. 业务能力总览；
6. 详细主业务流程；
7. 内部架构与子模块分解；
8. 目标模块实现细节；
9. 每个已确认子模块的独立详细设计章节；
10. 跨模块协作与端到端链路；
11. 全局对象、接口、状态、配置和构建索引；
12. 跨模块算法、并发、资源与性能；
13. 调试、可观测性和建议点读源码；
14. 功能、函数、图和证据覆盖；
15. 旧文档差异与功能演进，仅在提供旧文档时生成；
16. 假设、限制、风险和 owner-review 项。

每个主要章节以简短设计结论开头，以“读者现在应理解什么”和关键源码入口结束。引用必须来自实际读取或检索的证据，不得加入未读文档占位符。完整交付先完成每个设计单元的十四项内容草稿和证据表，再据此规划图，最后组装 Word；不得先建一个短 Word 后用剩余时间选择性补正文。

全局开篇负责建立认知；系统定位部分分别说明目标的系统架构位置、源码归属、所属上级模块、调用关系和 handoff；第 4 至第 8 章共同组成唯一 target module DesignUnit；第 9 章逐个承载 target-owned confirmed submodule 的本地完整细节；全局收尾只负责跨模块总结和索引。Target 的架构基础图属于第 4 章，唯一业务流程基础图属于第 6 章，第 7 章只分解 target 内部子模块且不占五视图槽位，数据/生命周期、代码流程和状态机属于第 8 章。第 8 章只引用第 6 章业务主图，不重复插入或计数。所属上级模块、全局对象表、接口表、代码流、状态机或性能章节不能替代 target 或任何已确认子模块的本地正文。关系分离与证据一致性检查适用于全文，不限于系统定位章节。

章节生成前必须核对集合恒等：架构介绍/分解表中的 confirmed 名称、冻结 census、unit 文件 ID、第 9 章详细章节 ID 和五视图账本 unit ID 完全相同。数量相同但名称被外部/context 单元替换仍是 `MISSING`，不得创建 Word。

## 2. 阅读路径模板

阅读路径必须包含四条路线：

- 大图理解：系统架构定位与模块归属 → 目标模块职责与架构 → 业务能力 → 详细主业务流程；
- 核心流程：详细主业务流程 → 内部架构与子模块分解 → 已确认子模块业务流程；
- 代码点读：设计对象与生命周期 → 函数/功能覆盖 → 代码流程 → 接口与协作；
- 调试性能：异常恢复 → 算法与性能 → 调试与可观测性 → 建议点读源码。

路线必须使用真实章节标题和内部链接，不得硬编码某个样例模块的名称。

## 3. 术语与范围表模板

```md
| 用户目标名 | 源码确认名称 | 缩写含义/UNKNOWN | 中文说明 | 所属上级模块/目标模块/子模块归属 | 证据 | 置信度 | owner-review 项 |
|---|---|---|---|---|---|---|---|
```

术语、翻译、缩写展开和所有权必须来自用户输入、源码、目录、注释或现有文档证据。未确认项使用 `UNKNOWN`、`low_confidence_review` 或 `not_confirmed`，不得写成确定结论。

## 4. 业务能力表模板

```md
| 能力ID | 能力名称 | 能力说明 | 所属设计单元 | 触发与前置条件 | 输入业务对象 | 主处理结果 | 状态/数据/资源副作用 | 失败或终止结果 | 源码证据 |
|---|---|---|---|---|---|---|---|---|---|
```

能力说明必须回答处理什么对象、为何触发、完成什么业务动作以及产生什么结果。禁止用函数名列表代替业务能力，也不设置固定能力数量。

## 5. 详细主业务流程模板

主业务流程章节先给目标模块完整业务闭环总图，再按源码支持的流程族逐个展开。每个流程族包含：

1. 流程目标与业务对象；
2. 触发与前置条件；
3. 参与模块和责任边界；
4. 输入、初始化与资源准备；
5. 主路径步骤；
6. 条件分支和跨模块 handoff；
7. 状态、数据和资源变化；
8. 等待、异步回调、重试、超时和取消；
9. 失败、恢复、回滚和清理；
10. 成功与其他终止结果；
11. 总览图、必要的分支/子流程图及图后解读；
12. 源码证据和未确认项。

流程数量由真实业务能力决定。主业务闭环不能被单个读写子流程、函数调用链或状态机替代。

## 6. 内部架构与子模块分解表

```md
| Discovery Signal IDs | Candidate ID | 子模块候选 | 源码位置 | 业务定位与职责 | 输入/输出 | 上游/下游 | 状态/资源所有权 | 确认结论与依据 | 排除原因/合并归属 | 深挖依据 | 详细章节 | 证据 | 置信度 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
```

子模块不能仅按目录名认定。必须先从业务能力、接口、构建/注册、初始化/清理、调用链、状态/事件、数据/资源所有权和错误恢复路径建立独立发现信号表，再把信号映射成候选全集。每个候选最终只能是 `confirmed_submodule` 或有证据的 `excluded_non_submodule`；合并必须保留原 Candidate ID 和归属。表后固定报告 `discoverySignalCount / mappedToCandidateSignalCount / evidencedNonSubmoduleSignalCount / unmappedDiscoverySignalCount` 和 `candidateCount / confirmedCount / excludedCount / unmappedCandidateCount`。候选行的 Discovery Signal ID 集合必须与信号表中映射到该候选的 ID 集合双向严格相等；确认行还必须唯一映射一个 confirmed-submodule DesignUnit ID。完整交付要求两类计数都闭环且两个 unmapped 均为 0。所有 `confirmed_submodule` 都必须链接到独立的连续详细设计章节和五视图覆盖账本。

## 7. Target module 和已确认子模块统一模板

Target module 及每个 target-owned confirmed submodule 按以下顺序输出；所属上级模块不使用本模板：

```md
### <设计单元名称>详细设计

#### 1. 简介与业务定位
说明该设计单元在所属范围中的作用、触发来源、处理对象、交付结果、典型异常和上下游衔接。

#### 2. 职责、非职责与边界
| 项目 | 说明 | 证据 |
|---|---|---|
| 主要职责 | | |
| 非职责 | | |
| 输入边界 | | |
| 输出边界 | | |
| 上游 | | |
| 下游 | | |

#### 3. 触发、前置条件、输入与输出
| 类型 | 对象/事件/状态 | 条件或语义 | 证据 |
|---|---|---|---|

#### 4. 内部架构、上下游与依赖
插入本设计单元架构图，并解释组件、边界、共享上下文、队列、缓存、适配层和依赖方向。

#### 5. 业务能力与完整业务流程
插入本设计单元业务流程图。图后解释主路径、关键分支、handoff、异常、等待、重试、恢复和终态。

#### 6. 核心对象、所有权与数据生命周期
对结构体、变量、队列、缓存、位图、表和配置对象说明字段语义、创建、初始化、读写、传递、并发、持久化、失效、回收和释放，并插入数据/生命周期图。

#### 7. 函数/功能覆盖与代码执行流程
列出范围内功能和函数覆盖，对关键函数说明签名、参数校验、局部状态、分支、循环、回调、写入、返回、错误和清理，并插入代码流程图。

#### 8. 状态、事件与状态机
说明状态所有者、dispatch、事件、guard、action、转换、副作用、非法/忽略事件、失败和恢复；插入状态机图或提供证据化 N/A。

#### 9. 接口与协作
分类说明外部、内部、跨模块、回调、异步、队列、通知及源码确认的适配接口。

#### 10. 异常与恢复
| 路径 | 触发条件 | 处理动作 | 状态/数据影响 | 终态 | 证据 |
|---|---|---|---|---|---|

#### 11. 算法、策略、配置、并发、资源与性能
说明目标、输入、规则、边界、失败路径、复杂度或性能影响、阈值、队列深度、容量、超时、热路径、瓶颈和调优项。

#### 12. 构建、注册、初始化与平台差异
说明构建目标、模块注册、初始化/停止/清理顺序、feature flag、条件编译、平台差异和集成边界。

#### 13. 调试、可观测性与点读源码
说明日志、计数器、断言、dump、诊断、失败症状，以及按问题类型推荐的源码入口。

#### 14. 源码证据、置信度与缺口
列出支持本单元的 SRC/CE/BR/ST/BF 证据、结论置信度、未覆盖内容和 owner-review 项。
```

以上十四项是语义字段，不是建议菜单。完整交付中，每个已确认子模块都必须出现且保持连续；不能因为它被归为非核心、辅助、平台相关、初始化相关或实现简单而省略。分解表中出现 `confirmed_submodule` 但没有对应连续章节，或章节缺少适用字段时，交付状态只能是 `PARTIAL/MISSING`。

以下内容均不构成完整正文：

- “简介 + 函数名列表”；
- “状态名列表 + 一个状态机图”；
- “结构体名/字段名列表”；
- “宏名称/阈值列表”；
- “接口名称 + 一句话职责”；
- 只有图题而没有图前问题说明、图后语义解读和源码依据。

关键函数至少说明职责、参数/返回、前置/后置条件、调用者/被调用者、分支/循环/异步完成、状态或数据副作用、错误/清理和行级证据。关键对象至少说明重要字段、创建/初始化、所有者、读写者、更新点、传递、并发、失效/回收/释放和关联流程。关键接口至少说明 caller/callee、调用时机、同步性、参数/结果、前后置条件、副作用、失败行为和证据。策略至少说明目标、输入、规则、边界、失败路径、性能/资源影响、调优项和证据。

状态章节必须包含转换表：

```md
| 当前状态 | 事件/触发 | Guard | Transition Action | 下一状态 | 状态/数据/资源副作用 | 失败/忽略事件 | 源码证据 |
|---|---|---|---|---|---|---|---|
```

只列出状态枚举、switch case 或 handler 名称时，本节不得标记为 `PASS`。

五类视图必须在对应的第 4 至第 8 小节就地出现。每个非 `N/A` 槽位至少有一张唯一主图；同一 PNG 不能跨设计单元或跨视图重复计数。每个真实入口/业务流程族、异步等待/回调/超时/取消链、独立异常/重试/恢复链、独立 FSM 域、所有权/生命周期族或实质不同的平台/初始化变体都必须登记独立 Signal ID，并生成聚焦详图或给出可审计的合并理由。状态机只接受持久控制状态的 `current state -> event/trigger -> guard/action -> next state` 证据；普通命令/type/handler 分派进入代码流程，不冒充 FSM。对有重要状态机的单元，状态机章节必须引用 dispatch、state-overview、transition-conditions、error/retry/timeout 和关键 handler 细节；不使用节点数、边数作为机械质量指标，但不得减少五类覆盖槽位或逐实例触发的聚焦详图。

## 8. 跨模块收尾章节

跨模块章节只保留：

- 端到端调用与业务 handoff；
- 接口矩阵和异步完成关系；
- 数据所有权与跨层传递；
- 状态交接和共享事件；
- 公共配置、构建和平台差异；
- 资源竞争、并发限制和跨模块性能影响；
- 全局调试入口和点读索引。

每行必须链接到拥有详细说明的目标模块或子模块章节。不得复制整段本地细节，也不得用该索引把本地覆盖标记为 `PASS`。

## 9. 功能、函数、图与证据覆盖

覆盖章节必须分别列出：

- 全部已识别功能点及其所属设计单元；
- 范围内函数/入口、深挖状态和证据位置；
- target module 和每个已确认子模块五类图状态；
- 关键图边的证据映射；
- `PASS / PARTIAL / MISSING / N/A`、缺失原因和下一点读位置。

名称列表、图数量或章节存在不能单独构成 `PASS`。正文必须实际解释对象生命周期、接口语义、分支、异常恢复、策略和证据。

## 10. 旧文档更新与差异

提供旧文档时，正文仍按当前源码重新构建。差异章节引用 `11-feature-diff-completeness-rules.md`，包含 Both、CodeOnly、DocOnly、旧符号演进映射、过期内容、当前新增能力、风险和待确认项。

## 11. 窄范围交付

- 单章节或单子模块：保留术语、范围、证据基线，只展开指定单元及适用视图；
- 状态机专项：保留状态所有权、dispatch、transition、handler、异常恢复和证据；
- 快速更新：披露跳过的分析、未读证据、未生成图和未执行的视觉 QA；
- 旧新差异：允许只输出差异报告，不强制生成新完整 Word。

窄范围请求不得被自动扩展为完整 Word，也不得改变 skill 调用机制或普通 QA。

## 12. Word 组装规则

使用真实 Heading 层级和目录。Target module 与每个已确认子模块必须保持连续，标题、图题、图片、图注和图后解读就地组装。所属上级模块只作为定位、归属和 handoff 说明，不能扩展为另一个主体章节。Word 中不得把所有业务图、代码图或状态机图集中到脱离所属单元的全局图集章节。所有章节、表格、图和结论都必须使用“所属上级模块”这一用户侧称呼，并分别核对系统位置、源码归属、调用和数据流证据。

在创建 Word 前冻结最终标题序列。非交付态 `*-working.docx` 必须预先包含所有最终 H1/H2/H3 标题，以及每个正文/表格批次的唯一普通段落锚点 `[[SBDD-CONTENT:<designUnitId>:<topicId>]]`，但不得包含图片。后续编辑只能使用 `replace_paragraph_with_blocks` 和精确 `paragraphText` locator 消费对应锚点一次；禁止使用 heading 后插入或文末 append 绕过缺失锚点。目标模块实现细节必须位于全部子模块章节之前，所有子模块必须按冻结分解表顺序连续出现。

逻辑正文可按以下文件组织，也可以合并为等价的 Word 章节：

```text
05-enhanced-detail-design/README.md
05-enhanced-detail-design/01-reading-path.md
05-enhanced-detail-design/02-terminology-scope-evidence.md
05-enhanced-detail-design/03-system-position-and-module-role.md
05-enhanced-detail-design/04-target-architecture-and-capabilities.md
05-enhanced-detail-design/05-main-business-flows.md
05-enhanced-detail-design/06-submodule-decomposition.md
05-enhanced-detail-design/07-target-implementation-details.md
05-enhanced-detail-design/08-confirmed-submodules.md
05-enhanced-detail-design/09-cross-module-summary.md
05-enhanced-detail-design/10-global-indexes.md
05-enhanced-detail-design/11-performance-build-observability.md
05-enhanced-detail-design/12-coverage-and-evidence.md
05-enhanced-detail-design/13-diff-and-evolution.md
05-enhanced-detail-design/14-assumptions-risks-review.md
```

完整 Word 任务必须在图形和 Word 阶段之前，把目标模块和每个已确认子模块分别保存为 `05-enhanced-detail-design/units/<designUnitId>.md`。每个文件都使用同一十四项模板，在相邻位置记录主题状态、解释和证据；`08-confirmed-submodules.md` 只保存有序索引，不能用一个汇总文件掩盖未完成单元。`02-source-evidence/module-scope.md`、这些 unit 文件以及输出根目录的 `resume-state.md` 和 `review-notes.md` 共同提供正文 readiness 证据；任何 applicable topic 为 `MISSING` 时 Word 状态保持 `not_started`。

全部正文锚点替换后、插图前必须执行逐标题 body audit。每个最终 Heading 的本地检查区间截止到下一个任意级别 Heading，区间内必须存在解释性正文；父级 DesignUnit 的十四项聚合覆盖另行跨子标题检查。图片、图题、图注、图号、空段落、目录、内容锚点以及单独的列表或表格不计正文，容器标题必须在首个子标题之前有方向性说明。空标题、只有图片、只有清单、只有表格或只有一句名称说明时，本节为 `MISSING/PARTIAL`，不得进入插图、TOC 或交付阶段。

## 13. 文字质量要求

- 图前说明图要解决的问题，图后解释业务意义、关键分支和源码依据；
- 不用固定字数、节点数、边数或子图数代替内容完整性；
- 不把函数名列表当作业务能力，不把字段名列表当作生命周期，不把宏列表当作性能设计；
