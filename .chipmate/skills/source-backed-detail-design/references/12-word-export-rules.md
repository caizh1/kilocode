# 12 Word Export Rules

> 完整源码详设 Word 由 `source_backed_design_job` 在全部工作项通过后一次性组装、校验和渲染。模型不得在该任务中直接执行本文件旧版 fragment/edit/merge 流程。以下公共 Word 工具规则只适用于单章节、旧文档更新或其他明确的窄范围交付。

## 1. ChipMate Word route

When the user asks for Word output, generate the `.docx` with ChipMate's generic Word tools. Use `create_word_document` for the initial working document and `apply_word_document_edits` for bounded non-image chapter batches. The tool-created working artifact is continuation evidence, not the final user deliverable. Do not introduce a task-specific Word pipeline, temporary JSON shell bridge, local Pandoc, local LibreOffice/soffice authoring, `pip install`, `npm install`, `python-docx`, or a standalone Python/Node DOCX script as the primary or fallback route. `08-word-export-input.md`, when used, is an auditable assembly draft, not the final export mechanism or tool payload.

For a full `D > 1` task, use bounded unit fragments instead of one oversized Word payload. On the final turn, the root creates the sole target base fragment with cover, `{{TOC}}`, opening chapters, target prose, and its exact approved PNGs. It then creates each uniquely named child fragment in frozen order from the persisted unit prose and exact approved PNGs; each child fragment removes generated Title, Subtitle, and author paragraphs through exact `delete_paragraph` edits and verifies its first non-empty block is its unique Heading 1. The root creates one similarly cover-free closing fragment, then calls `merge_word_documents` with target base first, child fragments in frozen census order, closing fragment last, and `separatorHeading: false`. It must reject any remaining extra cover, duplicate Title/TOC, out-of-order heading, missing body, incomplete figure result, or source count mismatch before field materialization. Fragment artifacts are working components, never deliverables.

## 2. create_word_document arguments

Before calling `create_word_document`, verify the required Word tools are exposed and prove prose readiness from `02-source-evidence/module-scope.md`, the frozen DesignUnit census, every `05-enhanced-detail-design/units/<designUnitId>.md`, and root-level `resume-state.md` plus `review-notes.md`. The resolved target must be distinct from every evidenced owning module; decomposition, census, unit, detailed-chapter and diagram-ledger sets must be identical. Every unit must have exactly fourteen separately headed topic IDs with the matching status as the next non-empty line and fourteen audit rows whose status sets are exclusive; topics 01–07/09–14 must be `PASS`, only topic 08 may be evidenced `N/A`, and `distinctTopicHeadingCount = 14`, `topicPassCount + evidencedTopicNaCount = 14`, `missingTopicCount = 0`. `PASS (N/A)`, non-state-machine N/A, and combined range/catch-all sections are incomplete. Prove business-flow readiness from a structurally valid `14-business-flow-family-census.csv` and `04-diagrams/business-flow-plan.md` with all flow gaps zero. Then require every DesignUnit ID in `completedFigureUnitIds`, every required row at `attempted_success` with a non-empty validated PNG and completed per-image review, `uniqueSuccessfulDiagramIdCount = successfulRenderedItemCount = requiredFigureCount`, and `unassignedSlotIdCount = pendingRenderSlotCount = missingRenderedPngCount = remainingRequiredFigureCount = duplicateDiagramIdCount = 0`. Batch-call count is orchestration evidence only and must never be compared with image count; each successful result item must map to exactly one required Diagram ID. A saved `.mmd`, syntax-success manifest, or `save_mermaid_artifact` result never counts as a rendered figure. An evidenced FSM `N/A` must have no Diagram ID, Mermaid source, PNG, caption, or Word image. Any missing or duplicate unit, topic, explanation, flow family, edge, handoff, terminal, evidence, diagram, rendered PNG, review, or safe workspace file-writing capability keeps Word state `not_started`; preserve the continuation state and do not call any Word tool, reserve a final filename, or declare a DOCX artifact. A working skeleton is not an exception.

Build object-shaped top-level arguments with the authoritative dynamic `title`, `language: "zh-CN"`, an informative dynamic `documentType`, `author`, `headingNumbering: "decimal"`, summary paragraphs, and `sections`; never wrap or stringify them. `documentType` must describe the source-backed scope actually covered, add information beyond the title, and never be only “详细设计”, a title repetition, a generic placeholder, or an unsupported claim. Pass `author: "ChipMate source-backed-detail-design"` by default so both the visible author line and DOCX creator metadata use that identity; an author explicitly supplied by the user takes precedence. Never invent an author containing ChipMate, ChipMate, or a similar variant. Choose a stable `taskSlug`; use a clearly non-deliverable `*-working.docx` output name during assembly and reserve the intended final filename for the completed field-refresh chain.

Keep a formal page-1 cover. Before the sole `{{TOC}}` item, include concise Normal-paragraph cover statements for document scope, current source baseline, and evidence status. Derive them from the frozen scope and evidence files; state a branch, revision, version, date, or clean/dirty status only when directly read from the current source tree. Otherwise use “当前工作树快照” or mark the fact `待确认`; never invent it. Keep these statements compact and do not place chapter prose, large tables, code, or images on the cover. The materialized TOC intentionally starts on page 2.

A `D = 1` full detailed design uses the text-only anchored skeleton path below. A `D > 1` task uses validated fragments above; within each fragment, prose must still precede image insertion and all mutations use the immediately returned path. The sole base cover contains the real title, informative subtitle, approved author, compact cover statements, and exactly one standalone `{{TOC}}` before Heading 1 `阅读路径`. Never create a Word section or Heading named `目录`, `TOC`, or `Contents`; `{{TOC}}` alone becomes the non-outline TOC heading.

For the `D = 1` skeleton path, fill non-image content in canonical order with strictly serial `apply_word_document_edits` calls and exact `replace_paragraph_with_blocks` anchors. For a unit fragment, `create_word_document` may receive that one already-audited unit's text blocks directly, but no image block; inspect its complete local body before inserting figures. In both paths, one unit is the maximum payload, every mutation uses the immediately returned path, structural edits cannot add images, and missing/ambiguous anchors or headings must be repaired rather than falling back to append.

When the last prose/table mutation succeeds, inspect before any image insertion. Require the complete frozen outline, zero `[[SBDD-CONTENT:*]]` paragraphs, `paragraphsTruncated: false`, `tablesTruncated: false`, completed DesignUnit count equal to the frozen census, and explanatory body in every final heading's own local range. Compare each DesignUnit's fourteen persisted topic IDs and explanations with its unit Markdown: Word must materialize them rather than replace them with one-line summaries or tables. Body means explanatory Normal/code paragraphs before the next heading of any level; aggregate fourteen-topic coverage is checked separately per DesignUnit. Empty paragraphs, directory material, image title/caption/figure ID, drawings, anchors, and standalone lists or tables do not count. Container headings require their own short orientation paragraph before the first child heading. Repair every empty, image-only, list-only, table-only, inventory-only, or one-line-name section before continuing.

Only after this body audit passes, insert every PNG serially through `insert_mermaid_into_word`. Pass the exact persisted PNG path returned by the successful source-backed render, the latest `wordPath`, unique existing H2/H3 `heading`, stable `taskSlug`/working `outputFile`, plain Chinese `figureTitle`, complete independent Chinese `altText`, and a visible caption containing the unique Diagram ID. Never omit `pngPath`, ask insertion to re-render, use base64, or substitute another path. The tool recovers the authoritative Mermaid source from the canonical batch result and rechecks its hash, so a process restart does not require the model to reproduce whitespace or escaping byte-for-byte. If multiple diagrams belong immediately after one heading, invoke them in reverse intended display order because each insertion is placed directly after that heading.

If a large call fails, reduce it to the text-only working skeleton rather than writing the payload to a temporary file or retrying the same oversized object. Split a failing chapter until the smallest meaningful topic anchor is isolated. If that mutation still fails, preserve the persisted Markdown unit files and exact continuation point, disclose the native tool error, and do not present the working DOCX as a deliverable. Do not replace the failed detailed subsection with a one-line summary or switch to a third-party generator.

Sections must preserve the hybrid structure from `10-detail-design-output-templates.md`: the opening positioning section separates system architecture, source ownership,所属上级模块, calls and target handoffs; chapters 4 through 8 together form the target module DesignUnit, with target architecture in chapter 4, its unique business primary in chapter 6, target-internal decomposition with no diagram slot in chapter 7, and target data/code/state views in chapter 8. Chapter 8 references the chapter-6 business figure without reinserting or recounting it. Chapter 9 then contains one continuous chapter per target-owned confirmed submodule in the exact frozen decomposition-table order, followed by cross-module summaries, indexes, coverage, optional differences, and review items. 所属上级模块 must not acquire target-style chapters or mandatory five-view images. Target implementation chapter 8 must never appear between child chapters, and a later child batch must never be appended after the closing global chapters. Do not assemble all submodule business flows, code flows, state machines, or objects into detached horizontal chapters. The relationship-separation rule applies throughout the document, not only to the opening positioning section.

New detailed-design documents use the Codex `standard_business_brief` baseline: US Letter portrait, one-inch margins, Calibri 11 pt body, the standard blue H1/H2/H3 hierarchy, real numbering, fixed-DXA tables, quiet running header, and right-aligned page number. Put the standalone `{{TOC}}` paragraph after the title/summary and before the first Heading 1 for a full detailed design. After all chapter and late-image mutations, call `materialize_word_fields` with `tocMode: "materialize"`, the stable `taskSlug`, and the stable `outputFile`. The result must be a native Word TOC field with a non-outline directory heading and page separation, not a static list of copied heading text.

Before materialization, inspection must prove exactly one correct Title, one non-empty and non-redundant Subtitle, the approved visible author, at least one evidenced cover statement, exactly one placeholder, `placeholderParagraphIndex < firstHeading1ParagraphIndex`, zero Heading 1 titles matching `目录|TOC|Contents`, and `阅读路径` as the first outline Heading 1. The Subtitle must not equal “详细设计” or the Title. After materialization and field refresh, inspection must prove `Title index < TOCHeading index < first Heading 1 index`, zero `{{TOC}}`, zero directory-named Heading 1, the TOC beginning on page 2, and no self-entry for the TOC heading. Any violation keeps the full Word unfinished and must be repaired before final delivery.

## 3. Existing-document update and difference output

For an existing-document update, rebuild conclusions from current source and use `apply_word_document_edits`, `apply_word_template_styles`, `materialize_word_fields`, `normalize_word_table_spec`, `merge_word_documents`, or `diff_word_documents` as appropriate. Preserve unrelated user content and styles where the request is a bounded edit. Do not regenerate unrelated chapters or use the old document as current implementation evidence.

A difference-only request may return the requested diff report without producing a new full Word document. A single-chapter, single-submodule, state-machine-only, or quick update uses the same generic Word tools and only the relevant sections; it must not be expanded into the canonical full-document outline unless the user asks.

## 4. Figures and diagrams

Track separate `CoverageSlot` and `DiagramRequirement` ledgers. `CoverageSlot` contains exactly `5D` base rows. `DiagramRequirement` contains one row per actual base or focused figure using `diagramId -> baseOrFocused -> owningSlot -> complexityInstanceIds -> sourceEvidence -> mmdPath -> sourceStatus -> syntaxValidation -> semanticCoverage -> pngPath -> visibleFigureId -> targetSection -> renderDisposition -> visualQaStatus -> wordInsertionStatus`. Do not put drawings into the initial working skeleton. After the complete text-only body audit passes, insert every successfully rendered required Mermaid diagram with this semantic payload:

```json
{
  "wordPath": "<latest working DOCX path>",
  "source": "<validated Mermaid source>",
  "pngPath": "<pngPath returned by render_mermaid_diagram>",
  "heading": "<unique existing H2/H3 heading>",
  "figureTitle": "中文图题",
  "caption": "[DU-<designUnitId>/<viewType>/<diagramId>] 中文图注",
  "altText": "完整的中文可访问性说明，源码符号保持原样",
  "width": 480,
  "height": 280
}
```

The stable visible figure ID appears exactly once, at the start of the caption; the title is plain Chinese and the alt text is a complete accessible description. Use the render result's cropped display width and height and retain pixel dimensions as QA evidence. Word insertion is inline, centered, aspect-locked, downscale-only, and bounded to 624 CSS px wide and 720 CSS px high. If fitting the page makes labels unreadable, split and rerender the diagram instead of shrinking it again. Keep `.mmd` paths in diagram indexes and evidence ledgers for traceability. Multiple figures under one heading are inserted in reverse desired order. If the user explicitly asks for Mermaid source in Word, use a normal code block with Mermaid source; otherwise rendered diagrams must be PNG images.

## 5. Render verification

For a new full document, the text-only working skeleton has no image relationships. Inspect immediately after creation and confirm that the complete frozen target/submodule heading sequence and every expected content anchor exist exactly once before filling prose. After prose filling, record zero remaining anchors and the heading-body audit before the first insertion. Derive `lateInsertedRelationshipIds` after each serial image insertion by set difference; after replacement record `replacedRelationshipIds` and verify that the relationship set did not grow; after an intended removal record only relationships actually absent as `removedRelationshipIds`. Replacing image content normally keeps the relationship ID, and deleting a paragraph or section does not prove its relationship was deleted.

After all prose, image, style, and field mutations, make the final `inspect_word_document` call with `maxParagraphs: 1000` and `maxTables: 200`. Require exactly one Title-style paragraph whose text equals the planned title, no `{{TOC}}`, no `[[SBDD-CONTENT:*]]`, no Heading 1 named `目录`/`TOC`/`Contents`, `阅读路径` as the first outline item followed by `术语、范围与证据基线`, exact frozen heading order, zero empty/bodyless heading ranges, completed DesignUnit count equal to the census, and no inspection, paragraph, or table truncation. A generic `truncated: true` is also failure. Compare final relationship IDs with the expected set using set difference, not planned-count arithmetic. `imageCount` is only a coarse relationship count; it cannot prove content completeness, drawing placement, or semantic identity.

All mutations of one DOCX must be serialized. Process required Mermaid figures as serial slot transactions so each `render_mermaid_diagram` semantic result is checked and bound to exactly one Diagram ID before continuing. Parallel calls that edit or insert into the same `sourcePath` are forbidden: each output is a sibling fork and later copies can discard earlier figures. Maintain one authoritative working path and pass the path returned by each successful `apply_word_document_edits`, `insert_mermaid_into_word`, style, or field operation into the next mutation. A disclosed coverage-slot, visible-ID, or unexplained relationship-delta mismatch is not completion; sequentially repair the specific defect and reinspect.

The post-repair inspection must compare the final outline, exact heading order, all fourteen local topics for every design unit, later cross-module chapters, per-heading explanatory body, unique caption-only figure-ID paragraphs, table count, and image relationship set with the planned document. It must reject a census that lists more confirmed submodules than complete local chapters, a heading range with no explanatory Normal/code paragraph, a chapter that contains only a name inventory/list/table/drawing/caption, and any target or child unit moved outside the frozen order. Call inspection with `maxParagraphs: 1000` and `maxTables: 200`; require `paragraphsTruncated: false` before using paragraph results as a complete body/visible-ID audit and `tablesTruncated: false` before using table results as complete. Reconcile each actual drawing occurrence to the ledger using `headingPath`, `caption`, visible `[DU-<designUnitId>/<viewType>/<diagramId>]`, `altText`, relationship ID, media path, and content hash. Require zero missing relationships, orphan relationships, missing media targets, duplicate visible IDs, and unexplained duplicate hashes. If either paragraph or table inspection remains truncated, the body audit is not complete and the document cannot pass; page images can diagnose layout but cannot prove missing source-backed prose. `imageCount` alone is insufficient.

For the full detailed-design Word workflow, call `render_word_document` after the relationship and outline checks. The tool tries the configured ChipMate Render Service first and the local LibreOffice/Poppler path second. Record the required `serviceBasicPageQaStatus` separately from optional `pixelReviewStatus`; the tool field `visualQaStatus: completed` means its basic page diagnostics completed, not human/model pixel review. The deployable basic gate requires `rendered: true`, `visualQaStatus: completed`, `pageEvidenceStatus: completed`, `pageCountKind: exact`, `pagePngPaths` complete and unique with positive equal expected/returned/saved page counts within `maxPages`, `fieldRefreshStatus: completed`, passing `textQa`, a valid `refreshedDocxPath`, equal nonzero `tocHeadingCount`, `tocEntryCount`, and `tocPageNumberCount`, and no error issue or blank-page, near-blank-page, page-summary-failed, image-loss-suspected, invalid/duplicate PNG, page-sequence, PDF-page-count, text-loss, or response-integrity diagnostic. Tool completion with `rendered: false`, `visualQaStatus: skipped`, incomplete page evidence, failed field refresh/text QA, missing pages, or invalid refreshed path is failure. Make only the verified refreshed DOCX authoritative, then repeat title, outline, TOC, drawing, relationship, unit-topic, truncation, and `validate_word_document` inspection. If the active model supports images, it may additionally read every page at 100% and complex figure/table/code pages at 200%; record this as enhanced pixel review. If no vision model exists, set `pixelReviewStatus: unavailable` and continue only when the complete Render Service basic gate passes. Report `qaLevel: render-service-basic` and explicitly disclose that subtle clipping, overlap, tofu, and appearance were not pixel-inspected; never call the basic result human visual PASS.

## 6. Success criteria

A completed Word handoff reports the final non-empty `.docx` path returned by the complete serial create/edit/repair/render-refresh/validation chain, final `validate_word_document` status, `artifactStatus`, `acceptanceStatus`, confirmed and completed DesignUnit counts, fourteen-topic local coverage, empty-heading count, remaining-content-anchor count, discovery/candidate closure counts, base-view and focused-figure counts, required rendered count, late/replaced/removed/final relationship sets, service-basic-reviewed count, optional pixel-reviewed count, missing count, bounded repairs, paragraph/table truncation status, final render QA status, `qaLevel`, and any pixel-review limitation.

For a requested full Word, any false readiness, remaining content anchor, bodyless heading, incomplete unit, malformed flow census, missing/failed/service-unreviewed PNG, invalid TOC, truncated inspection, failed field refresh, skipped basic page QA, Render Service defect diagnostic, or XML error means no final-name DOCX, no final artifact declaration, and no Word path. Absence of an image-capable provider alone is not failure; it lowers the disclosed QA level to `render-service-basic`. The Word tool may already have created an internal working artifact manifest; treat it only as continuation evidence, not as `artifactStatus: generated` or a deliverable. Persist the Markdown units and first incomplete item instead. `PARTIAL` is the unfinished task status, not permission to hand off a full-Word artifact. A narrow text-only Word is allowed only when the user explicitly requested that reduced deliverable before assembly. While native tools remain available and bounded attempts have not failed, continue from the first unresolved item. A Markdown draft, Mermaid source, ASCII diagram, temporary JSON file, `08-word-export-input.md`, or `*-working.docx` alone is not a Word deliverable.
